# Versions: MVVM vs VIPER

Практические выводы после реализации одного и того же приложения (Counter) на двух архитектурах.

---

## MVVM (Model-View-ViewModel)

### Структура
```
Model (данные)
  ↓
ViewModel (логика + реактивность)
  ↓
View (UI, подписка через @StateObject)
```

### Плюсы
-  **Быстрая разработка** — меньше кода (3 файла на модуль)
-  **Реактивность из коробки** — @Published автоматически обновляет UI
-  **Простая для понимания** — линейный поток данных
-  **Идеально для маленьких проектов** (до 20-30 экранов)
-  **SwiftUI friendly** — нативная интеграция через ObservableObject

### Минусы
-  **ViewModel может разрастись** (Massive ViewModel проблема)
-  **Смешение ответственности** — логика + форматирование + навигация в одном месте
-  **Сложнее тестировать** — нужно мокировать ObservableObject
-  **Масштабируется хуже** на больших проектах

### Когда использовать
- Простые экраны (формы, списки, детали)
- MVP/прототипы
- Проекты до 30 экранов
- Solo разработка

### Код (пример ViewModel)
```swift
class CounterViewModel: ObservableObject {
    @Published var counter: CounterModel
    
    func increment() {
        counter.value += 1  // Всё в одном месте
    }
}
```

## VIPER (View-Interactor-Presenter-Entity-Router)

### Структура
```
View (UI)
  ↓
Presenter (медиатор)
  ↓
Interactor (бизнес-логика)
  ↓
Entity (данные)

Router (навигация)
```

### Плюсы
-  **Чёткое разделение ответственности** — каждый компонент делает одно дело
-  **Отличная тестируемость** — легко мокировать через протоколы
-  **Масштабируемость** — подходит для больших проектов (50+ экранов)
-  **Командная разработка** — разные люди могут работать над разными компонентами
-  **Явные зависимости** — через протоколы, видно кто с кем общается

### Минусы
-  **Много boilerplate кода** — 6+ файлов на модуль
-  **Медленная разработка** — нужно написать все компоненты и протоколы
-  **Сложность для новичков** — нужно понимать всю цепочку
-  **Оверкилл для простых экранов** — усложнение без реальной пользы

### Когда использовать
- Крупные проекты (50+ экранов)
- Команды из 3+ разработчиков
- Когда нужна максимальная тестируемость
- Enterprise приложения

### Код (пример потока)
```swift
// View → Presenter
presenter.incrementButtonTapped()

// Presenter → Interactor
interactor?.increment()

// Interactor: логика
counter.value += 1
presenter?.didUpdateCounter(value: counter.value)

// Presenter → View
view?.updateCounter(value: 5)
```

##  Мои выводы

### Что понял на практике

**MVVM:**
- Писать код на MVVM **в 2-3 раза быстрее** чем на VIPER
- @Published — магия, но **скрывает поток данных** (сложнее дебажить)
- Для учебных проектов и MVP — **идеальный выбор**

**VIPER:**
- **Первый раз тяжело**, но потом привыкаешь к структуре
- Явные вызовы через протоколы — **отлично для понимания потока данных**
- Для реального продакшена в крупных компаниях — **стандарт**

**SwiftUI + VIPER:**
- Нужен **ViewState класс** как мост (ObservableObject)
- Struct View не может напрямую соответствовать протоколам с мутацией
- Решение работает, но добавляет слой абстракции

## Рекомендации для выбора архитектуры

**Используй MVVM если:**
- Проект до 30 экранов
- Solo разработка или маленькая команда (2 человека)
- Нужна быстрая разработка
- SwiftUI проект
- Стартап/MVP

**Используй VIPER если:**
- Проект 50+ экранов
- Команда 3+ разработчиков
- Высокие требования к тестированию
- Enterprise приложение
- Долгосрочная поддержка (5+ лет)

**Гибридный подход (реальность):**
- Простые экраны (Settings, Profile) → MVVM
- Сложные модули (Payments, Chat) → VIPER
- Общие компоненты → Clean Architecture

## Clean Architecture

### Что это
Архитектурный подход с разделением на 3 слоя:
- **Domain** — бизнес-логика (UseCases, Entities)
- **Data** — инфраструктура (Repository, DataSource)
- **Presentation** — UI (MVVM/VIPER)

### Ключевые принципы
- **Dependency Rule**: зависимости направлены ВНУТРЬ (от UI к Domain)
- **Domain не зависит** от UI, БД, фреймворков
- **Инверсия зависимостей**: Domain определяет интерфейсы (протоколы), Data реализует

### Плюсы
- Бизнес-логика полностью изолирована
- Легко менять UI (SwiftUI → UIKit)
- Легко менять источник данных (memory → UserDefaults → CoreData)
- Максимальная тестируемость (каждый слой отдельно)
- Переиспользование UseCases между MVVM и VIPER

### Минусы
- Много слоёв = много файлов
- Сложность для простых задач (оверкилл для To-Do app)
- Требует глубокого понимания принципов

### Clean MVVM vs Clean VIPER

**Clean MVVM:**
```
UseCases → ViewModel → View
```
- Проще, меньше компонентов
- ViewModel напрямую использует UseCases

**Clean VIPER:**
```
UseCases → Interactor → Presenter → View
```
- Больше слоёв разделения
- Interactor изолирует UseCases от Presenter

### Когда использовать Clean Architecture
- Крупные проекты (100+ экранов)
- Долгосрочные проекты (5+ лет поддержки)
- Команды 5+ разработчиков
- Когда бизнес-логика сложная и критичная
- Когда нужна миграция UI или источников данных

---

### Что использовать в реальных проектах?

**Для учебных проектов / MVP:**
→ Простой MVVM

**Для стартапов (до 50 экранов):**
→ MVVM + отдельные UseCases для сложной логики

**Для средних проектов (50-100 экранов):**
→ Clean MVVM

**Для крупных корпоративных проектов (100+ экранов):**
→ Clean Architecture + VIPER для сложных модулей

**Гибридный подход (как в Яндекс):**
- Settings, Profile → MVVM
- Payments, Analytics → Clean VIPER
- Shared business logic → Domain layer
